Der Mail-Baukasten

Wie E-Mail-Vorlagen künftig aus Notion-Daten entstehen statt aus Code — und wie n8n und das Editor-Tool stl mail dieselbe Quelle lesen.

01

Ausgangslage

Annabell hat mit email-builder.html ein Werkzeug gebaut, mit dem sich E-Mails aus Komponenten (Überschrift, Text, Button, Status-Label, Crew-Signatur) zusammensetzen und als fertiges HTML exportieren lassen. Es funktioniert gut für die Gestaltung — hat aber drei strukturelle Grenzen:

  • Vorlagen leben als JavaScript-Presets im Code des Tools, nicht als Daten. Eine neue Vorlage bedeutet: die HTML-Datei öffnen und Code ändern.
  • n8n kann diese Vorlagen nicht lesen. Deshalb liegt der Mail-Text für z. B. den Login-Link oder die "Neues Ticket"-Bestätigung noch einmal separat, hart codiert, in den n8n-Workflows — eine dritte Kopie desselben Inhalts.
  • Jede inhaltliche Änderung (andere Formulierung, neuer Baustein) braucht jemanden, der die Exportdatei erneut in den Workflow einträgt. Kein gemeinsamer, aktueller Stand.

Es gibt zwar bereits eine Notion-Datenbank Mail Templates — dort liegt aber pro Zeile ein komplettes HTML-Dokument als Textblock (genutzt z. B. für den monatlichen "Website Performance Radar"-Report). Das löst das Problem nicht: der Inhalt ist zwar in Notion, aber weiterhin ein undurchsichtiger HTML-Klumpen statt einzelner, wiederverwendbarer Bausteine.

02

Die Idee

Design und Inhalt werden getrennt und beide wandern nach Notion — aber in zwei verschiedene Tabellen, weil sie sich unterschiedlich oft und von unterschiedlichen Leuten ändern:

  • Mail-Komponenten — wie ein Baustein-Typ aussieht. Ändert sich selten, typischerweise wenn sich das visuelle Design ändert.
  • Mail-Vorlagen (+ ihre Blöcke) — was in einer bestimmten Mail steht und in welcher Reihenfolge. Ändert sich oft, ist reine Redaktionsarbeit.

n8n und das Editor-Tool lesen dieselben drei Notion-Tabellen und benutzen exakt denselben Rendering-Code — die Vorschau im Editor ist also, byte-genau, das, was beim Versand entsteht.

03

Datenmodell

Drei neue Notion-Datenquellen unter der Seite ✉️ stl mail builder:

Mail-Komponenten

ein Baustein-Typ pro Zeile
  • Name — „Fließtext“
  • Design HTML — <tr><td>…
  • Feldschema — JSON
  • Beschreibung
  • Status — Active/Draft

Mail-Vorlagen

eine Mail pro Zeile
  • Name — „Neues Ticket“
  • Betreff
  • Webhook-Slug — „neues-ticket“
  • Banner aktiv / Variante
  • Footer aktiv
  • Status

Mail-Vorlagen-Blöcke

ein Baustein-Einsatz pro Zeile
  • Vorlage — Relation
  • Komponente — Relation
  • Reihenfolge
  • Aktiv
  • Inhalt — JSON
Mail-Vorlagen-Blöcke verbindet die anderen beiden — „Neues Ticket = Überschrift + Text + Button + Crew, in dieser Reihenfolge“

Diese Aufteilung ist absichtlich Notion-nativ: Annabell sieht in der Vorlagen-Ansicht die Blockliste als normale, sortierbare Unterzeilen — kein Datenbank-Wissen nötig, um zu verstehen, woraus eine Mail besteht.

Technischer Stolperstein Die Notion-API lehnt es ab, eine Text-Property zu speichern, deren kompletter Inhalt sich als JSON-Array oder -Objekt parsen lässt (offenbar eine interne Validierungs-Heuristik, kein dokumentiertes Verhalten). „Feldschema“ und „Inhalt“ tragen deshalb ein technisches json:-Präfix, das lib/notion.js beim Lesen/Schreiben transparent entfernt bzw. ergänzt. Wer die Notion-Tabelle direkt öffnet, sieht diesen Präfix — die eigentliche Bearbeitung findet aber ohnehin im stl mail-Editor statt, nicht in der rohen Notion-Zelle.
04

Zwei Platzhalter-Ebenen

Zwei Arten von Platzhaltern kommen im selben Text vor, dürfen aber nicht verwechselt werden:

SyntaxBeispielWoWird ersetzt durch
[[feld]] [[text]] „Design HTML“ einer Komponente den Inhalt eines einzelnen Blocks — einmalig, beim Zusammenbau der Mail
{{TOKEN}} {{TICKET_URL}} „Betreff“/„Inhalt“ in Notion echte Werte aus n8n — erst beim tatsächlichen Versand, bleibt bis dahin sichtbar stehen

Ein Beispiel aus der Vorlage „Neues Ticket“ macht den Unterschied greifbar. Der Fließtext-Block trägt in Notion als Inhalt: 

{ "text": "wir haben deine Anfrage als neue Aufgabe angelegt: **{{TICKET_TITEL}}**", "weight": "regular" }

Beim Rendern setzt die Komponente „Fließtext“ diesen Wert an die Stelle von [[text]] in ihrem Design-HTML. {{TICKET_TITEL}} bleibt dabei unangetastet stehen — das übernimmt erst der zweite, spätere Schritt, wenn n8n den echten Ticket-Titel aus dem Webhook mitschickt.

05

Rendering-Pipeline

Ein Aufruf, vier Schritte — identisch, ob im Editor oder für n8n:

Vorlage + Blöcke laden
→
jeden Block mit seiner Komponente rendern
→
Banner + Blöcke + Footer zusammensetzen
→
Laufzeit-Tokens ersetzen

Der komplette Code dafür liegt an einer Stelle: lib/mail-render.js im Repo stl mail — bewusst ohne Node- oder Notion-Abhängigkeiten, damit dieselbe Funktion unverändert im Browser (Live-Vorschau) und auf dem Server (/api/render für n8n) läuft. Es gibt also keine zweite Kopie der Rendering-Logik, die aus dem Takt geraten könnte.

06

n8n-Integration

Heute schreibt z. B. der Workflow „Stadtteilliebe Inside – Neues Ticket Benachrichtigung“ den Mailtext direkt in den Send-Email-Node. Migration in einem Schritt: ein HTTP-Request-Node vor dem Send-Email-Node ruft POST /api/render auf — 

{ "slug": "neues-ticket", "tokens": { "contactName": "{{ $json.body.contactName }}", "title": "{{ $json.body.title }}", "ticketUrl": "{{ $json.body.ticketUrl }}", "projectName": "{{ $json.body.projectName }}" } }

— und übernimmt subject/html aus der Antwort. Ab diesem Zeitpunkt kann Annabell den Wortlaut einer Mail in Notion ändern, ohne dass jemand den n8n-Workflow anfassen muss. Diese Umstellung ist bewusst nicht Teil dieses ersten Schritts — die bestehenden Workflows laufen unverändert weiter, bis die Redaktion in Notion sich bewährt hat.

07

Das Repo: stl mail

Next.js-App nach demselben Zuschnitt wie stl-inside/stl-prism, gegen dieselben drei Notion-Tabellen:

  • / — Liste aller Vorlagen.
  • /templates/[id] — Editor: Vorlage-Metadaten, Blockliste mit ↑/↓-Reihenfolge, Aktiv-Schalter, schema-generierte Eingabefelder je Baustein, Live-Vorschau als iframe, plus ein Testdaten-Feld, das die Laufzeit-Tokens simuliert.
  • /components — Design HTML und Feldschema der Bausteine pflegen.
  • POST /api/render — die Schnittstelle für n8n.

Bewusst nicht in dieser ersten Version: Drag&Drop-Umsortieren (Pfeiltasten reichen für die kleinen Blocklisten), Undo/Redo, eine eigene UI für Status-Badges (kommt vorerst als JSON-Textfeld). Alles Verbesserungen, die sich nachrüsten lassen, sobald der Grundaufbau sich in der Praxis bewährt hat.

08

Stand & nächste Schritte

Bereits erledigt:

  • Die drei Notion-Tabellen sind angelegt, unter der bestehenden Seite „✉️ stl mail builder“.
  • Fünf Komponenten sind eingerichtet (Überschrift, Fließtext, Button mit Link, Status-Label, stl Crew) — 1:1 aus dem bisherigen email-builder.html übernommen.
  • Die zwei bestehenden Vorlagen „Login“ und „Neues Ticket“ sind mit ihren Blöcken befüllt und bereit zum Testen.
  • Das Repo stl mail ist aufgesetzt: Editor, Komponenten-Verwaltung, Render-API, Build läuft grün.
Ein manueller Schritt fehlt noch Die Notion-Integration hinter dem NOTION_TOKEN von stl-inside/stl-prism hat noch keinen Zugriff auf die drei neuen Tabellen — Notion verlangt das pro Seite explizit. In Notion einmalig: Seite „✉️ stl mail builder“ öffnen → ••• → Verbindungen → dieselbe Integration hinzufügen, die auch stl-inside nutzt. Danach läuft npm run dev im Repo stl mail gegen echte Daten.

Danach, in Ruhe und nicht Teil dieses Schritts:

  • Den n8n-Workflow „Neues Ticket Benachrichtigung“ auf /api/render umstellen.
  • Weitere bestehende Mails (Ticket-Status-Wechsel) als Vorlage nachbauen.
  • Die alte, flache Mail Templates-Datenbank (Website Performance Radar) bleibt vorerst unverändert bestehen — anderer Anwendungsfall, kein Baukasten-Bedarf erkennbar.
